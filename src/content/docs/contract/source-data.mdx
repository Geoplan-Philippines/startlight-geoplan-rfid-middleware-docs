Provider-native master data in; Geoplan-owned mapping and adaptation.

<Aside type="note" title="No shared provider schema">
  ETP POS and Samooha do not need to implement Geoplan field names, response envelopes, query parameters, pagination, timestamps, deletion tombstones, or snapshot metadata. Geoplan adapts to each provider's existing source contract.
</Aside>

## Integration boundary

The provider makes its product master data available through an existing supported read method. This may be an API, database view, export, or another approved source. The source remains authoritative and keeps its current structure.

Geoplan owns the connector and adapter that:

- authenticates using the provider's supported method;
- retrieves the available master data;
- maps source records to the middleware's internal product model;
- handles the source's existing pagination, cursors, exports, or full-load behavior;
- stores checkpoints or comparison state where needed;
- keeps the local copy synchronized;
- adds EPC/TID associations outside the provider's product model.

## Source concepts Geoplan maps

| Concept | Provider representation | Geoplan handling |
| --- | --- | --- |
| Product identity | Existing source identifier or business key | Maps to the middleware's internal product identity. |
| Barcode or GTIN | Existing barcode field, relationship, or value where available | Maps to the internal barcode/GTIN representation. |
| Product details | Existing names, categories, variants, sizes, colors, statuses, and other attributes | Maps only the fields required by the RFID workflow. |
| Change signal | Existing timestamp, version, cursor, event, export cadence, or no incremental signal | Uses the available mechanism; otherwise compares full source data. |
| Deletion or inactivity | Existing status, omission, deletion flag, history, or other source behavior | Interprets the provider's native behavior; no Geoplan tombstone fields are required. |
| Pagination or batching | Existing source convention, if any | Follows the provider convention in the connector. |

The names and structures above are concepts to discover, not fields the provider must add.

## Adapter discovery inputs

Geoplan uses the following information to configure each source-specific adapter:

- environment-specific access location and approved read method;
- authentication, credential rotation, and network requirements;
- a representative payload, export, or sample query result;
- an existing data dictionary or field documentation, when available;
- the meaning of product identifiers and barcodes;
- how to retrieve the complete product set;
- existing pagination, batching, filtering, and ordering behavior;
- how updates, inactive products, and deletions appear in the source;
- rate limits, timeouts, maintenance windows, and availability expectations.

This documents the source as it exists. It is not a request to reshape the provider data.

## Validation

Geoplan validates the adapter against the provider source by confirming that it can:

- retrieve and map the complete available product master;
- preserve provider product identities and barcode relationships;
- process the provider's actual paging or batching behavior without gaps;
- detect changes and removals using the behavior the source already exposes;
- resume safely after authentication, connectivity, throttling, or source failures.

Any source-specific assumptions remain in the Geoplan adapter configuration and mapping documentation.
